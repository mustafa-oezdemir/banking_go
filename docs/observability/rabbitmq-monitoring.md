# RabbitMQ monitoring: what, why, and how

## What is monitored?

RabbitMQ publishes its own Prometheus metrics using the built-in `rabbitmq_prometheus` plugin. It runs on port `15692` inside the Docker Compose network. That port is deliberately not mapped to the host.

Prometheus uses two scrape jobs every 15 seconds:

- `rabbitmq` reads aggregate broker/node metrics from `/metrics`.
- `rabbitmq_notification_queues` reads detailed metrics only for `notification.payment.v1`, `notification.payment.retry`, and `notification.payment.dlq` from `/metrics/detailed`.

The focused set gives the payment-notification path enough visibility without creating a metric series for every RabbitMQ object. The broker updates its internal statistics every 10 seconds, which is compatible with the 15-second scrape cadence.

## Why are both endpoints used?

`/metrics` is the normal, low-cardinality endpoint and is the right source for broker availability. `/metrics/detailed` adds per-queue values such as ready messages and consumers. It is filtered in Prometheus because unrestricted detailed scraping can make monitoring expensive as queues, connections, or consumers grow.

## Dashboards and access

Start the stack with `docker compose up --build`. Then open:

- [Prometheus targets](http://localhost:9090/targets) to check both RabbitMQ jobs are `UP`.
- [Grafana](http://localhost:3001) and sign in with `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` from your ignored `.env` file.

Grafana provisions:

1. **RabbitMQ-Overview** — the official RabbitMQ Overview dashboard, vendored from the RabbitMQ project. Its imported `${DS_PROMETHEUS}` datasource placeholder is mechanically replaced with the provisioned `prometheus` datasource UID so it works without an import dialog.
2. **DemoBank - RabbitMQ Messaging** — queue depth, DLQ backlog, and consumer count for the three queues used by this project.

`GRAFANA_ADMIN_PASSWORD` is generated by `start.ps1` when missing or still a placeholder. Change it in `.env` for any non-disposable environment; it must never be committed.

## Operational signals

| Signal | Interpretation | First response |
| --- | --- | --- |
| `up{job="rabbitmq"} = 0` | Prometheus cannot scrape the broker metrics endpoint. | Check `docker compose ps rabbitmq`, then broker logs and network health. |
| Ready messages increase on `notification.payment.v1` | Consumer is slower than producers or unavailable. | Check notification-service health/logs and consumer count. |
| `notification.payment.retry` grows | Delivery is transiently failing and retry routing is active. | Check SMTP/Resend configuration and notification logs. |
| `notification.payment.dlq` is non-zero | An event exhausted retries or is malformed. | Inspect the event safely, correct the cause, then replay deliberately. |
| Consumers are zero | No active notification consumer. | Restore notification-service; do not roll back booked payments. |

The metrics contain technical queue names and counts only. Do not add addresses, balances, tokens, email bodies, IBANs, or payloads as labels.
