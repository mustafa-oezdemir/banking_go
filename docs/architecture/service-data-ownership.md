# Service Data Ownership

Phase 8 makes database ownership enforceable as well as documented. The local stack still uses one PostgreSQL **instance** for developer simplicity, but runtime services connect through different PostgreSQL roles and only receive `USAGE` plus DML permission on their owned schema. The `db-role-provisioner` and `migrations` containers are deployment-control-plane components, not application services; they run with the administrator credential before runtime services start.

| Service | PostgreSQL role | Owned schema/tables | Permitted cross-service data flow |
| --- | --- | --- | --- |
| Banking | `banking_app` | `public`: customers, accounts, payments, ledger, audit, outbox | Private Identity provisioning HTTP command; RabbitMQ events/notification commands |
| Identity | `identity_app` | `identity`: users, credential hashes, sessions, reset tokens | Private Banking provisioning HTTP command; Notification password-reset command |
| Notification | `notification_app` | `notification`: processed-event deduplication state | RabbitMQ event consumption; explicit email command API |

The role grants deliberately deny schema usage outside this table. Consequently a SQL `SELECT`, `JOIN`, or write to another service's private schema fails at the database boundary even if an implementation mistake reaches a SQL client. The Banking service is the only owner of the `public` schema, so Account, Payment, Ledger and Outbox retain their local ACID unit of work.

## Operations

- Runtime credentials are `BANKING_DB_PASSWORD`, `IDENTITY_DB_PASSWORD`, and `NOTIFICATION_DB_PASSWORD`; they are separate from the PostgreSQL administrator password and generated by `start.ps1` for local setup.
- Apply schema changes through the `migrations` Compose service. It runs after role provision and before application services.
- Changing an application credential is safe: update its environment value, rerun Compose, and `db-role-provisioner` updates the PostgreSQL role password without changing grants.
- In a production deployment, use one PostgreSQL database or cluster per service when independent backup, scaling, or compliance boundaries justify the additional cost. The code and roles already do not rely on cross-schema queries.

## Automated safeguards

- `backend/internal/architecture/dependencies_test.go` checks private persistence-adapter boundaries.
- `backend/internal/platform/database/data_ownership_test.go` checks the applied schema privileges in the integration database.
- Migration `000015_enforce_service_data_ownership` revokes default/public access and grants schema-local privileges only.
